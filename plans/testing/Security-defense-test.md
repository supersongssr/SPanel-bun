## 1. 压测场景设计

为了完全打通防御链路，测试人员需要建立以下三个具有代表性的攻防测试环境：

```text
[ 压测攻击器 (模拟千级别 IP / Bot 集群) ]
                │
                ├─── (场景一: 模拟垃圾包无 POW 攻击) ────► [ 触发中间件拦截, 要求 CPU 极低 ]
                │
                ├─── (场景二: 模拟混合合法 POW 慢速攻击) ──► [ 触发难度自动调高至 5 阶, 肉鸡算力耗尽 ]
                │
                └─── (场景三: 模拟登录用户刷单查询 API) ───► [ 触发 Redis 滑动窗口, 返回 429 ]
```

## 2. 压测工具准备 (`wrk` 与 `hey`)

我们推荐使用高性能的 L7 压测工具，这两者能提供精确到微秒级的延迟监控与数万级的并发支持：
1. **wrk**：基于 C 语言编写，多线程超高并发，采用 epoll 事件循环机制，非常适合模拟大规模并发。
2. **hey**：基于 Go 语言，界面直观，适合发起指定总请求数量的梯度请求验证。

## 3. 场景一：恶意无 POW 登录接口暴力扫频压测

### 3.1 攻击模拟目标
向后台频繁上报不带 `powSalt` 和 `powNonce` 的垃圾参数登录包，或携带不正确哈希值的废料请求，验证后台的秒级丢弃机制，防止密码 Argon2 加密层拖垮系统。

### 3.2 压测执行命令 (wrk)
编写 Lua 脚本 `wrk_script.lua` 模拟 POST 垃圾数据请求：

```lua
-- wrk_script.lua
wrk.method = "POST"
wrk.headers["Content-Type"] = "application/json"
wrk.body = '{"email":"attacker@spam.com","password":"any_raw_password"}'
```

在测试终端中发起高并发测试（12 线程，500 并发，压测 30 秒）：
```bash
wrk -t12 -c500 -d30s -s wrk_script.lua http://YOUR_STAGING_SERVER/api/v1/auth/login
```

### 3.3 预期防御响应
1. **响应码比例**：`400 Bad Request` 占比必须是 100%。
2. **请求处理延迟**：99% 的请求耗时（Latency）应该**低于 2 毫秒**。
3. **系统消耗**：在每秒 20,000+ 的高频请求下，由于在 CPU 密集的 Argon2 运算之前就已经被 POW 中间件拦截，后端 Bun 进程的 CPU 使用率应**低于 10%**。

## 4. 场景二：高负载攻击下 POW 自适应难度提升测试

### 4.1 攻击模拟目标
测试系统在高并发攻击流量冲击下，能否自适应调高 POW 前导零难度值，强制客户端消耗算力。

### 4.2 压测执行流
1. 发起并发对后台敏感接口（如 `/api/v1/auth/send-code`）进行请求。
2. 当后端系统的 CPU 利用率瞬间突破设定的防御阀值（如 70%）或 Redis 请求监控计数超过 200 次/秒时，查验获取 POW 挑战接口（`GET /api/v1/auth/pow-challenge`）下发的参数。

### 4.3 验证结果标准
*   **自适应触发**：获取到的 `difficulty` 属性必须能自动从最低难度（如 `3`）自适应地提升至高阶防御难度（如 `5`）。
*   *测试提示*：可以使用 `hey` 工具模拟 100 个慢速合法解题连接，观察服务器在难度提升后，并发吞吐量自动暴跌，说明攻击源的算力正在被极大抑制。

## 5. 场景三：已登录用户 API 限流及 Redis 锁拦截验证

### 5.1 攻击模拟目标
已登录的用户如果写脚本不断调用查询节点（`GET /api/v1/user/node`）或敏感的订单购买接口，必须在到达 Redis 限速瓶颈时被精确压制。

### 5.2 压测执行命令 (hey)
携带合法的测试账号 JWT 令牌，并发 20 线程对节点列表接口进行持续刷新：

```bash
hey -n 200 -c 20 -H "Authorization: Bearer YOUR_VALID_TEST_JWT" http://YOUR_STAGING_SERVER/api/v1/user/node
```

### 5.3 预期防御响应
1. **滑动窗口触发**：前 20 次请求成功，返回 `200 OK`，第 21 次请求开始，接口直接返回 `429 Too Many Requests`，响应头携带 `Retry-After: 60`。
2. **安全隔离**：即使该账号遭遇了 429 限流处罚，同一局域网下的其他测试账号应**完全不受影响**，能继续正常访问，说明基于 UID 分组的 Redis 滑动窗口在物理上达到了完美隔离。

## 6. 服务器监控指标与应急响应指标

在压力及防 CC 攻防演练进行期间，系统运维需通过 `top`、`htop` 及 `netstat` 监控以下红线指标，一旦任何指标跌破红线，必须立刻优化相关逻辑层配置：

| 监控指标对象 | 稳定安全状态指标 | 临界红色警戒指标 | 异常响应策略 |
| :--- | :--- | :--- | :--- |
| **MySQL 连接数** | < 20 个活跃活跃连接 | > 150 个（连接池满） | 检查节点同步队列是否堵塞，Worker 事务回写是否堆积 |
| **Redis 内存负载**| < 128 MB | > 1.5 GB | 检查滑动窗口 ZSet 的 ZREMRANGE 垃圾清理是否未正常执行 |
| **Bun 进程 CPU 占用**| < 30% | > 85% | 验证无 POW 参数的请求是否进入了 Bcrypt/Argon2 计算层 |
| **系统响应时延** | < 15 ms | > 200 ms | 开启 Nginx 静态文件 gzip/brotli，阻断特定高频攻击 IP段 |
